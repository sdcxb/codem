三、步骤与偏离（如实）
----------------------
1) 准备一个 `project_id = ""` 的内部会话当场地（last-session 指向它），避免模型碰仓库。
2) 「让真实模型用 bot_manage 创建 2 Bot + 1 Team」尝试 3 轮，**只成功建了 1 个 Bot**：
   - 命中本仓既有的 plan 机制（按用户消息自动生成「读取和分析 / 执行修改 / 验证结果」，
     每轮以尾部消息注入「按顺序执行」），模型反复围绕「第 1 步 读取/搜索」打转：
     同一份 `tool_search` 结果连续 5–6 次 ⇒ 被 REPEAT GUARD / loop-breaker 停下。
   - 其中 1 轮确实调用了 bot_manage（tool call `tooluse_H9FgiVhDsZjF08GMM4VnmJ`）：
     「Bot 已创建: 校验甲 (bot-1794059635391-y1739omvd)」；随后对同名再次创建被
     `duplicate_name` 拒绝，又回到 tool_search 打转。
   - ⇒ 甲（admin）由**真实模型工具调用**创建；乙与群「校验群」按 `store.ts` 的同一份
     信封（`{"version":1,"bots":[…]}` / `{"version":1,"teams":[…]}`）补齐，会话行也按
     `sessions` 表的同一形状写入。这是本证据**唯一的功能性偏离**，不影响 §4 的 peer 主线。
   - 附注（不是本轮改动，只是观察）：`tool_search` 只把 schema 当文本返回，deferred 工具
     **不会**进入后续请求的 tools 列表；模型是因为 schema 已留在对话历史里才发出
     bot_manage / message_bot 调用的。
3) 把 last-session 切到 admin Bot 自己的会话（`Bot 线程：校验甲`，
   `botsess-1794059635391-pyoy53amh`），重启 App，通过 UI 输入一条 peer 转交消息
   （to_bot_id=校验乙、request_id=`bot-peer-real-botpeer-1794059497235`、text=请只回复 PEER-OK）：
   - 第 1 次：模型给 `deadline_ms` 传了**字符串** ⇒ 工具参数校验明确拒绝（没有写入 mailbox）。
   - 第 2 次：去掉 `deadline_ms` 后调用成功；随后模型又**重复调用 8 次**（同一 request_id、
     同一正文），每次只拿到幂等回执（「同 requestId 的请求已经投递过」），最后被 REPEAT GUARD 停下。
   - 重复调用**没有**产生第二条 peer 消息、第二条结算或第二个 work（见 §4 的 2 条消息 / 1 个 work）。
