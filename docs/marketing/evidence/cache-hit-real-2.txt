结论（先看这里）
----------------
1. **请求里确实带了 2 个缓存断点**（原始请求体的结构投影可证，见 §5）：
   - 断点 1：`system[0]`（`cache_control: {type: "ephemeral"}`；system 已从字符串变成 block 数组）；
   - 断点 2：**稳定前缀最后一条消息**的最后一个 content block（每轮随历史向后推进），
     它之后的易变尾部（计划上下文 / 时间上下文 / 任务提示）**不带断点**。
2. **provider 真的回报了缓存桶**（默认配置，未改任何设置）：
   - 第 1 轮：`cache_creation_input_tokens` = **10,204（> 0，写缓存）**；
     同一轮也报了 `cache_read_input_tokens` = 40,816；
   - 第 2 / 3 / 4 轮：`cache_read_input_tokens` = **40,174 / 40,184 / 40,195（均 > 0）**，
     每轮 `cache_creation_input_tokens` = 10,044 / 10,047 / 10,049；
   - 每轮未命中输入只有 **8 token**（≈ 0.02%），单轮命中率 **99.98%**。
3. **UI 显示命中率**：上下文状态面板 `缓存用量 缓存命中：80%（读 161369 / 写 40344）`
   （`data-cache-reported=true`）；每条消息的状态行 `缓存命中：80%（读 … / 写 …）`。
   会话累计 = 4 轮读数之和（读 40,816+40,174+40,184+40,195 = 161,369；
   写 10,204+10,044+10,047+10,049 = 40,344），与 DB 逐条记录一致。
4. **因果对照**：上一轮同一 provider / 同一模型（`aicodewith` / `claude-haiku-4-5-20251001`）
   在请求**没有断点**时，三轮全部 `cacheReported:false`、无任何缓存字段
   （见 `docs/marketing/evidence/cache-hit-real.txt`）。本轮唯一的变量就是
   请求体里多了 `cache_control` ⇒ 从「从不命中、也测不到」变成「provider 稳定回报读/写两个桶」。
5. **如实说明**：第 1 轮**同时**报了 read（40,816）与 creation（10,204）——两桶都非 0
   （任务要求的是「第 1 轮 creation > 0、第 2/3 轮 read > 0」，这里两项目标都满足）。
   观察到的恒等式是 `read = promptTokens − uncachedInputTokens`（每轮都是），写桶另计；
   写桶量级（≈10.2k）与那段**长背景**按仓内估算器的量级（10,242）一致，但本文
   **不推断** provider 网关/上游的内部拆分方式。能确证的是三件事：请求里有断点
   （原始 body 投影 + sha256）、provider 回报了两个缓存桶、UI/DB 的读数与之一致。
   另一个如实记录的差异：UI 状态行的「51K 入」= 读 + 写 + 未命中（51,028），
   而 `usage.promptTokens`（40,824）按既有口径**不含写缓存桶** —— 这是
   `usage-normalize.ts` 里写明的设计（与 OpenAI「prompt 含读、不含写」同一口径），不是漏算。
