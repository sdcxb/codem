================================================

结论（先看这里）
----------------
1. **链路已支持解析缓存字段，但本机默认 provider 本轮没有上报缓存字段。**
   - 默认 provider（`aicodewith`，Anthropic Messages 协议）连续 3 次真实调用里，
     `usage` 里一个缓存字段都没有（无 `cache_read_input_tokens` / `cache_creation_input_tokens` /
     `prompt_tokens_details.cached_tokens` / `prompt_cache_hit_tokens`）。
   - 因此**不能**声称「第二轮命中前缀缓存」——本轮没有可用的真实命中读数。
     本文只证明：**解析链路可用、未上报时界面不再自报 0%**（旧实现正是自报 0%）。
2. 每轮落库的形状是 `cacheReported:false`、读/写桶 **键不存在**（不是 0），
   会话累计 `cacheReadTokens=0 / cacheWriteTokens=0 / cacheReported=false`。
3. UI 两种状态：
   - 真实机（未上报）：ContextMonitor 显示 `provider 未上报缓存字段`（`data-cache-reported=false`）；
   - 夹具（上报）：`CACHE-UI-1` 断言 `缓存命中：66.7%（读 1200 / 写 300）`。
4. 判据（fixture，含变异自证）证明解析与两态显示可用：
   - `src/test/cache-hit-observability.test.ts`（11 条：Anthropic/OpenAI 形状、缺报、非法值、
     TokenTracker/CostTracker/Loop 累计、`streamAnthropic`/OpenAI 兼容流、聚合误报回归）；
   - `src/test/context-monitor-cache.test.tsx`（2 条：上报态 / 未上报态）。
   - 变异：去掉 `prompt_tokens_details.cached_tokens` 分支 ⇒ CACHE-OBS-2 红；
     去掉 `streamAnthropic` 的 `mergeUsage(message.usage)` ⇒ CACHE-OBS-7 红；
     把未上报文案改成 `缓存命中：0%（读 0 / 写 0）` ⇒ CACHE-UI-2 红。均已实测红后还原。

为什么不能归因于「provider 不缓存」
----------------------------------
- 本仓的 Anthropic Messages 请求（`aicodewith-protocols.ts::toAnthropicMessages`）**没有**
  发送 `cache_control` 断点，只做消息形状转换；若上游要求显式断点才创建/复用前缀缓存，
  那它本来就不会产生可读的缓存桶。
- 本轮响应里也确实没有任何缓存字段（message_start / message_delta 的 usage 都只有
  `input_tokens` / `output_tokens`）。
- 因此本文只声明**观察结果**：「该 provider 在本次调用中未上报缓存字段」。
  **不**声称「provider 没有缓存能力」，也不伪造命中率/命中数。

边界
----
- 单次 A/B、单模型（Claude Haiku 4.5 via aicodewith）、单会话，不能外推为「所有 provider 都不上报」。
- 未验证「显式 cache_control 后上游会不会返回缓存桶」；那是请求侧行为改动，不在本波范围。
- 真实命中率/省钱的结论需要 provider 上报缓存字段后才成立；本波只把「能不能看见」接通并如实显示。
