04 / 交付对账

大任务一分工，
为什么收尾总是散的？

不是 Agent 不会写，是每个 Agent 都只看自己那一小块：代码说完成、文档说完成、测试说通过，合起来却不是同一个版本。Codem 用任务状态、共享产物和统一完成清单来收口。

01 / 问题在哪

不是“各说各话”，是“各自完成、没人对账”。

多 Agent 最常见的失败不是某个 Agent 不会写，而是分工后没有一张总账：代码在一个手里，文档在另一个手里，测试没人收尾；每个人都只对自己的局部负责。

  • 代码 Agent 说“改完了”，但没更新架构文档；
  • 文档 Agent 说“补完了”，但不知道代码已经换了接口；
  • 测试 Agent 说“通过了”，但测的是旧版本；
  • 任务看板上全是“完成”，交付物却对不上。
所以问题不是“多 Agent 会不会聊天”，而是“有没有统一的完成条件”。 没有完成条件，Agent 越多，版本越容易分叉。
02 / 任务状态

任务要有领取、尝试、回滚，不能只说“我在做”。

一个任务被 Agent 领取时，会生成一个尝试编号。这样旧尝试的结果不会覆盖新尝试；领取失败可以回滚，不会把成员永久留在“正在工作”。

Task {
  id, title, status,          // pending / running / done / failed
  owner, attemptId,           // 谁领的、第几次尝试
  dependsOn: ["outline"],
  acceptance: ["代码可跑", "文档已同步", "引用已核验"],
  result: "artifact://..."
}
  • 领取：同一任务只允许一个有效领取；重复派发不重复执行。
  • 尝试：旧尝试结果不能覆盖新尝试；失败可重试，但结果不确定时不自动重试。
  • 回滚：领取失败/成员失活时回滚状态，不留下“假工作中”。
  • 依赖：前置任务没完成，后续任务不能假装开始。

03 / 共享产物

交接的是文件和任务，不是聊天记录。

把一个任务交给另一个 Agent，不应该靠“我把聊天记录发给你”。Codem 的交接是：目标、输入、产物、验收标准。文档、代码、测试、决定，都是同一种工作产物。

产物

文档版本、代码 diff、测试日志、引用清单。每个都有位置、版本和来源。

任务

谁领的、做到哪、依赖谁、验收条件是什么。任务状态不靠聊天猜。

Agent 读产物、写产物；共享的是工作台，不是整段上下文。每个 Agent 只拿自己需要的切片，避免把整个项目复制进每个窗口。

04 / 文档对账

代码完成，不等于任务完成。

大任务最容易漏的是收尾：架构文档、CHANGELOG、接口说明、示例。代码已经往前走，文档还停在上一版；下一个接手的人看到的是旧结论。

Codem 把「完成」写成一张清单：

  • 代码：改动、测试、回归结果；
  • 文档：相关章节、CHANGELOG、接口说明是否同步；
  • 引用：新增/修改的结论是否有来源；
  • 版本：文档版本和代码版本是否对齐，差异是否解释。
任一项没同步，任务保持“待补齐”，不能标完成。 这不是让 Agent 多写几句文档，而是把文档更新变成任务状态的一部分。
05 / 独立验收

写的人不验自己，验的人不参与写。

验收角色独立检查：代码能不能跑、文档有没有同步、引用是否支持结论、覆盖有没有缺口。发现缺口就退回，而不是“整体看起来不错”。

  1. 接收产物代码 diff、文档版本、测试日志、引用清单。
  2. 按清单核验完成条件逐项过；未同步的文档、无来源的结论、未跑的测试都算缺口。
  3. 退回或通过缺口退回给对应 Agent；通过才更新任务完成状态。
  4. 留审计谁验的、验了哪些、依据什么，都能回看。
为什么独立：写代码的 Agent 容易只验证自己改的部分；独立验收看的是“整体交付”，尤其是文档和版本有没有对齐。
06 / 边界与代码

它不是什么，以及落在哪。

  • 不是 Agent 越多越好。 小任务一个 Agent；只有大文档/多角色/并行才值得分工。
  • 不是群聊当协调层。 群聊适合人看；任务状态必须落在任务记录里。
  • 不是自动批准。 高影响动作仍需用户/策略批准；验收不能代替权限。
