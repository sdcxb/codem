CODEM / 实现细节

一条对话，
背后是怎么接住的。

从一次请求出发，说明 Codem 怎么保存对话、怎么取当前材料、什么时候压缩或换段、旧内容怎么找回来，以及文档、记忆和 Agent 怎么共用这些记录。

01 / 对话与工作段

你看到一条对话，模型看到的是一段工作上下文。

先把两个词说清楚：对话主线是你在界面上看到的那一条聊天；工作段是模型内部实际拿到的一段上下文。它们不是两个聊天窗口。

Codem 里，一条对话仍然是一个 Session。当这段上下文接近模型上限时，Codem 不会新建一个对话，而是在同一个 Session 里写一个“上下文检查点”（ContextEpoch），把模型看到的内容换到新的一段。

// 逻辑关系，不是数据库表结构
Session（对话主线，用户看到的那一条）
  ├─ ContextEpoch 1  kind="compact"   // 段内压缩
  ├─ ContextEpoch 2  kind="switch"    // 换到新工作段
  └─ ContextEpoch 3  kind="switch"
       cutoffMessageId = "msg_..."       // 从这条消息之后开始看

这里最关键的是 cutoffMessageId：它不是按时间猜，也不是按摘要位置猜，而是按消息 id 定位。模型从哪条消息开始看，是可以精确复现的。

你看到的（时间线）

所有消息都在，包括被压缩掉的旧消息。可以搜索、可以回读、可以导出。对应 listTimelineMessages。

模型看到的（投影）

只取最新检查点之后的 marker + 尾部消息。对应 listMessages / ContextView。

为什么不每次换段都新建 Session？ 因为对话记忆、侧边栏、远程查看、分叉都挂在 Session 上。新建 Session 会把“换工作段”变成“换对话”，用户和记忆都会被切断。Codem 的做法是：Session 不变，只换模型看到的那一段。
基础已落地：检查点、cutoff、完整时间线；自动换段仍在推进
02 / 压缩与换段

快满的时候，到底发生什么？

不是“到 80% 就弹窗”，也不是“所有情况都压缩”。Codem 先判断当前任务做到哪，再在两个动作里选一个。

动作什么时候用发生什么
压缩
compact		任务还没做完，但上下文里有很多可以收起来的过程写一个检查点摘要；保留最近原文和关键用户消息；旧消息不删，模型从检查点之后继续。
换段
switch		任务告一段落，或连续压缩后上下文仍然太满写一张交接单；带上最近原文和锚点；在同一个 Session 里开新工作段；旧段仍可查。
  1. 先量当前占用把系统提示、工具定义、输出预留都算进去，而不是只数聊天字数。占用接近上限才进入判断。
  2. 看任务是否真的结束不是看模型说“完成了”，而是看用户要求、未回答的问题、还在跑的工具和验收条件。没结束，优先压缩；结束，才考虑换段。
  3. 写交接单目标、限制、已完成、未完成、关键决定、关键文件、下一步、去哪里查。不是只写一句“已完成登录改造”。
  4. 保留最近原文交接单负责“理解”，最近原文负责“语气、细节、刚说过的话”。两者都要有。
  5. 换段，但不换对话新工作段从交接单和尾部消息开始；旧消息仍在时间线。用户继续输入，输入不会丢。
当前实现状态：压缩路径已有检查点和完整时间线；自动判断“压缩还是换段”属于路线图，当前版本仍以压缩为主。页面不把未完成的能力写成已上线。
自动切换：设计完成，分阶段落地
03 / 一次真实请求

把一次真实请求拆开看。

假设你说：「把年度报告第 4 节改一下，补上回滚方案，别动前面的结论。」

  1. 先记下这句话它进入当前对话主线，成为这一轮的任务描述；当前任务状态从「等待」变成「修改第 4 节」。
  2. 只取相关材料最近几轮对话 + 第 4 节原文 + 文档账本里第 1～3 节已确认的结论 + 两条相关记忆（格式偏好、必须可回滚）。不会把整本报告塞进来。
  3. 模型读和改先 doc_read 第 4 节的范围，再生成修改；需要引用时回到页码/段落。改动写进文档，不直接覆盖旧版本。
  4. 写回记录对话记录、工具结果、文档 diff、第 4 节状态（已改/待核验）都落下来；账本记下这次改动依据的来源。
  5. 核验再回复核验角色检查：第 4 节有没有漏掉「回滚」、有没有和前面结论冲突、引用是否支持。通过后才把结果和引用一起回复。
这一轮里，模型没有「记住整本报告」。 它只需要知道：第 4 节在哪、前面确认了什么、这次改了哪、依据是什么。其余内容留在文档和账本里，下一轮还能查。
文档读取/账本已有基础；完整的分节编译与核验仍在推进
04 / 旧内容

旧内容没有消失，只是不再全部塞给模型。

这是“长对话”能成立的前提。Codem 保留完整时间线，再提供不同的回读方式：

  • 时间线：按顺序看所有消息，包括被压缩的旧消息。
  • 全文检索：按关键词找旧对话；中文按字符/词组处理，不要求先分词。
  • 锚点：交接单里记录“第几段、第几条”，需要时直接回到原文。
  • 工具结果：长输出落在磁盘/记录里，模型需要时按定位读取，而不是一直占着上下文。

检索不是“自动把所有旧内容重新注入”。它更像查资料：先搜到，再读那一段，最后把引用带回当前回答。

边界：检索依赖关键词和锚点，不是语义上“什么都能想起来”。所以交接单要写清楚“去哪里查”，而不是只写结论。
05 / 长文档

长文档：先拆结构，再分节写，最后对账。

300 页文档不会被塞进一次请求。Codem 先把它变成可定位的结构，再用一本账把“读过什么、写过什么、验过什么”记下来。

文档先变成结构

目录、章节、段落、表格、页码、引用，都是可查询的坐标。模型可以先用 doc_outline 看目录，再用 doc_search 找相关段落，最后用 doc_read 只读需要的那几段。

再记一本账

每节记录：有没有读过、有没有改过、有没有核验、引用了哪些来源。写第 5 节时，先看账本和前面已确认的事实，而不是重新读完整本。

长任务怎么跑

大纲 → 分节任务 → 合并 → 一致性检查 → 引用核验 → 覆盖检查。每一节可以独立做，但共享同一本账和同一组来源。哪节没读、哪句没来源，账本里能看到。

完成条件里要有文档

代码任务不能以「测试通过」单独收尾。架构文档、CHANGELOG、接口说明、示例，都要在完成清单里。文档账本记录当前版本和最后一次核验；代码改动后，相关文档若没更新，任务保持「待补齐」，不能标完成。

这解决的是版本失配：开发版本已经往前走，文档还停在旧结论。把文档更新做成任务状态，而不是靠人临下班前想起来。
不是“向量检索就够了”：向量能找到相似段落，但接不上章节关系、术语和前后结论。结构 + 账本 + 引用，才是长文写作能收口的原因。
文档结构/检索/账本已有基础；完整编译流水线仍在推进
06 / 记忆

记忆：一条有出处的记录，而不是一句全局摘要。

“用户喜欢简洁”可能是对的，但如果没有来源、范围和有效期，它就会在别的项目里乱用，或者和后来的要求冲突。

写入

自动提取只产生候选；项目级/高影响的写入需要批准；手动写的记忆优先。自动流程不会删除或静默改写手动记忆。合并和归档要留下可撤销的记录。

读取

先按作用范围过滤，再按相关度、来源、时效和使用情况排序。回答时带引用；两条记忆冲突时，把双方都摆出来，而不是选一个偷偷覆盖。

不会发生

自动把“用户可能喜欢 A”写成全局事实，然后在所有项目生效。

会发生

在某个项目里记下一条有来源的决定；换项目时不带过去；冲突时保留双方。

作用域/审批/检索已有基础；完整记忆图谱与冲突视图仍在建设
07 / Agent

多 Agent：共享任务和文件，不共享整段聊天。

多 Agent 最容易出的问题，不是“不会写”，而是分工后没人对账：代码、文档、测试各在一个 Agent 手里，谁都说完成了，合起来却对不上。Codem 用任务状态和产物交接：目标、输入、验收标准、结果文件。

任务有状态

任务可以领取、开始、完成、取消、转派。每次领取生成一个尝试编号；旧尝试的结果不能覆盖新尝试。领取失败要回滚，不能把成员永远留在“正在工作”。

角色分开

负责人拆任务、写作角色产出、核验角色独立检查引用和覆盖。核验不自己批自己；发现缺口就退回，而不是“整体看起来不错”。

产物是共享的

文档、代码、测试结果、决定记录，都是同一种工作产物。Agent 读产物、写产物，不靠把整段对话转发来同步。

验收时，除了看代码能不能跑，还要看对应文档有没有更新、引用有没有补、版本号有没有对齐。文档没同步，任务就不算完成。

为什么不用群聊当协调层：群聊适合人看，但不适合做精确的任务状态。谁领了、试到第几次、结果有没有交回，必须落在任务记录里。
任务板/领取/回滚已有基础；群聊和完整产物协作仍在推进
08 / 可靠性与验收

怎么防止“说过了，但没做到”。

长任务最怕的不是报错，是静默地漏掉、重复或假装完成。Codem 把关键动作做成可检查的记录：

  • 上下文记录：这次请求带了哪些来源、哪些版本、哪些被裁掉，能复盘。
  • 写入顺序：先记录意图，再写文件/索引；失败可恢复，不出现“写了一半”。
  • 幂等：同一个任务重复派发，不会执行两次；结果不确定时不自动重试。
  • 验收：文档有覆盖账本，Agent 有独立核验，宣传承诺有 claims gate。代码任务还要检查文档是否同步，避免代码和文档两个版本。

这些不是“让模型更聪明”，而是让错误更早暴露、更容易退回去。

09 / 边界

它不是什么。

把边界说清楚，比把能力说满更重要。

  • 不是无限注意力。 单次请求仍然受模型窗口限制；Codem 做的是把旧内容放到可检索的地方，每次只取需要的。
  • 不是自动记得一切。 检索可能漏；所以交接单要写“去哪里查”，关键结论要带锚点。
  • 不是零成本。 压缩、换段、检索、核验都要花时间；省的是用户重新解释和重做的成本。
  • 不是所有能力都已上线。 首页表达目标形态，详情页按“已落地 / 部分落地 / 路线图”标注。
判断标准：不要看它说“支持长任务”，要看它能不能在换段后找回旧事实、在长文档里指出未核验章节、在记忆冲突时保留双方、在任务失败时回滚。
