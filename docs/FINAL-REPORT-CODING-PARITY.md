## 1. 结论（一段话）

**主判据成立**：12 个任务里**没有任何一格**是"对手稳定通过（2/2）× 我们稳定不过（0/2）" ✓。
配对看 **赢 0 · 输 1 · 平 11**，精确符号检验 **无显著差异**（P(赢≥0|1)=1.000、P(输≥1|1)=0.500）；

⇒ 在预先声明的口径下，"**不弱于** DSH"**成立** ✓；但**不能**说成"更强" ✗（没有一格是我们更稳）。
成本面：token 为对手的 **30%** ✓、工具调用 **48%** ✓、时延 **1.47×** ✗。

同时，本目标的**前置里程碑**（不经 eval 的实现）在同一个构建里复核通过 ✓：
`tools/audit/no-eval.mjs` 扫 `src` **命中 0 处** ✓；CSP 为
`script-src 'self' 'unsafe-inline' 'wasm-unsafe-eval' blob:` —— **不含裸 `unsafe-eval`** ✓。

## 4. 到底是什么起了作用（以及四个被证伪的方向）

**唯一被证明有效的机制：`[同族判据]`（1.16.245）** —— 当它**编辑**了某个源码文件之后，
用它**刚改的那个文件里的符号**去 grep 一次，把"**也提到这些符号的测试/判据文件**"以事实列出来 ✓。

- 依据：对照臂赢 repo-02 的那次，用的一次**按符号的 grep**（"Found 117 matches"）⇒
  匹配清单里同时出现源码与测试文件 ⇒ 它直接去读了 `dsh-d9-multi-edit-partial-failure.test.ts` ✓；
- 效果：**repo-02 首次连续两轮通过**（245 ✓），该格从"他们更高"变成打平 ✓；
- 为什么它不同于前四个：它由**它自己的动作**触发、内容与它刚做的事**直接相关** ✓。

**被证伪的四个方向**（都是"把信息送到眼前"，共花掉约四轮 4 小时的跑批）：

| 机制 | 版本 | repo-02 |
|---|---|---|
| 关键词命中清单（只搜测试文件） | 236 | 机制在装机版**静默失效** ✗（前端 `node:fs` 是桩） |
| 小族把成员全列出 | 237 | 1/2（波动） |
| 红了之后再放一次族提醒 | 243 | **0/2** ✗ |
| 每族一条"可以一起跑"的命令 | 244 | **0/2** ✗ |
| 全仓库搜索 + 源码命中 | 244/124 波 | 任务的中文描述词**在仓库里根本不存在** ✗ ⇒ 搜不到 |

**另外两次修正（值得写下来）**：
- 我曾判定"装机版**不跑** TS 的 `AgenticLoop`" ✗ —— 那是**我的监听挂在了被驱动杀掉的旧实例上** ✗；
  正确做法是"先跑驱动、等实例起来、再挂监听" ✓。
- `debugLog` 的开关是**模块加载时读一次** ✓ ⇒ 排查期间必须"先设 flag 再重启应用" ✓。

## 5. 残余弱点（如实列出，不粉饰）

1. **repo-02 仍差 1 轮**（我们 1/2、对手 2/2 ✗）：它在 232/237/243/244/245/246 上的读数是
   1、1、0、0、2、1 ⇒ **轮间波动很大** ✓；245 里连续两轮通过 ✓、246 里又掉一轮 ✗。
   它不是"稳定做不出"（不构成主判据违规 ✓），但**也不是稳定做得出** ✗。
2. **没有任何一格是我们更稳** ✗（赢 0）：最好也只是打平 ✓ ⇒ 只能说"不弱于"，不能说"更强" ✗。
3. **时延慢 1.47×** ✗（375–414s vs 282s）：token 与工具调用都更省 ✓，但墙钟更慢 ✗
   （与本应用每轮重建上下文、以及更保守的验证节奏有关 ✓，尚未收）。
4. **repo-04 两边都做不出**（0/2 vs 0/2 ✓）：这一格对结论中立 ✓，但说明还有一个共同难点未解 ✓。
5. **样本量**：每格 2 轮 ⇒ 单格结论只能当"不稳/稳定"来读 ✓，不能给单格下强结论 ✓
   （所有判定都按§13.16 的稳定性口径 ✓）。
6. 五个机制里**只有第五个有可测效果** ✓ ⇒ 前面四个的投入（约 4 轮跑批）是沉没成本 ✓。
