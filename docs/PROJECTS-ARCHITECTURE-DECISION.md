# ADR：Codem 要不要 Projects 化（2026-10-22）

- 状态：**Proposed — 机制已验证，报告可信度仍有缺口（gate 重验未做），暂不转 Accepted**
- 决策人：产品/架构（本仓由用户拍板）
- 关联：`docs/CLAUDE-PROJECTS-BENCHMARK.md`、`docs/CODEM-FEATURES.md`、`docs/COORDINATOR-P0.md`

## 1. 问题

Claude Code Projects 把“项目”变成一个**有协调者的长期容器**：协调对话拆任务、并行 thread 执行、项目记忆/指令跨 thread、Overview 按“是否等你”聚合。

Codem 现在是**会话平铺**：项目只是文件夹，用户自己当协调者。要不要改、改成什么样，是这次要拍板的事。

## 2. 三个候选

### A. 会话平铺 + 增强任务中心（不改模型）

- 保留“一个任务一个会话”，把 TaskCenter/委派/Inbox 做得更强；
- 优点：零迁移、零新概念、风险最低；
- 缺点：长项目仍然没有“负责人”；跨会话状态靠用户记；并行 thread 的验收/归因没有统一入口。

### B. 项目 = 协调者 + 并行 thread（Claude Projects 形态）

- 项目强制有一个协调者会话，所有工作必须从它派生 thread；
- 优点：入口唯一、状态集中、最接近已验证的 Claude 形态；
- 缺点：强制改变用户习惯；单会话小任务也要经过协调者，开销大；与 Codem 本地/自由会话文化冲突。

### C. 混合：项目**可选**协调者，thread 仍是普通会话

- 项目默认仍是文件夹 + 会话；用户可显式创建一个“协调者会话”；
- 协调者只读项目状态（brief/记忆索引/thread registry/报告/gate），不读聊天记录；
- thread 是普通会话，可 worktree 隔离，通过 `project_report` 汇报；
- Overview 是项目状态的一个视图，不强制所有会话进入；
- 优点：保留现有工作流；需要长项目的人获得协调能力；状态可人工检查/迁移；
- 缺点：两套入口需要解释；协调者与普通会话的边界要靠 UI 说清。

## 3. 决策

**选 C（混合、本地优先）。**

理由：

1. 实验证明“协调者上下文可重建”成立（brief + 报告 + gate，9000 字符内），但**没有证明**“所有任务都该经过协调者”；
2. Codem 的差异点是本地工具/技能/MCP/worktree，不是云沙箱；强制 Projects 形态会丢掉这个优势；
3. 混合模式可以先用一个真实项目验证，再决定是否提高协调者的默认地位；
4. 迁移成本最低：协调者是会话角色，不是新容器；现有会话不需要搬。

**如果 MVP 验证失败（协调者上下文仍频繁失真/用户不用），回退到 A，不继续投入 B。**

## 4. 目标用户与场景

- 单人开发者，在一个仓库里同时推进 3–8 个相关任务（功能、文档、测试、发布）；
- 任务跨多轮、跨天，需要“上次做到哪、谁在等我、哪些验收过了”；
- 不愿意把代码/凭据交给云端，仍要本地 worktree 与工具。

**不是**为团队协作、云端长跑、PR 自动合并设计。

## 5. MVP 范围（必须）

| # | 能力 | 验收 |
|---|---|---|
| 1 | 项目状态 | `.codem/project/` 有 brief/state/gates/events/reports，可人工读 |
| 2 | 协调者会话 | 项目行可创建；标题/角色可见；强制主工作区 |
| 3 | 协调者上下文 | 只读项目状态；≤9000 字符；真机 prompt 含 brief |
| 4 | thread 报告 | `project_report` 工具写 v3.1；坏报告拒绝且可见 |
| 5 | Overview | 按“待你/运行中/待评审/已完成”聚合 thread |
| 6 | worktree | thread 可隔离；改动可合并/冲突收口 |
| 7 | 端到端 | 一个真实项目 3+ thread 跑通，协调者能回答“谁在等我/哪些 gate 过了” |

## 6. 明确不做（至少这一版）

- 云 sandbox / 云端 thread；
- PR 自动创建、CI 自动修复、review 评论处理；
- 多用户/团队权限；
- 强制所有会话进入项目协调者；
- 自动合并冲突（只做选边/人工收口）。

## 7. 迁移与兼容

- 现有会话不改表、不搬家；协调者只是项目状态里的一个 session id；
- 删除协调者会话时清空指针；普通会话不受影响；
- 项目状态是本地文件，默认可删；不进入 git（`.gitignore`）。

## 8. 成功指标（MVP 验证）

1. 协调者重建：新开协调者会话，只读状态即可回答“当前有几个 thread、谁在等我、哪些 gate 过了”；
2. 上下文：协调者 prompt ≤9000 字符项目段，且不包含 thread 聊天正文；
3. 报告可信：至少一次“线程声称 done 但无日志证据”被契约拒绝；
4. 冲突：至少一次同文件冲突按 blocked/选边收口，主工作区不被留在冲突态；
5. 使用成本：普通会话路径不增加步骤；协调者路径只多“创建协调者”一次点击。

## 9. 风险

- **双入口困惑**：用户不知道何时用协调者。缓解：项目行只放一个皇冠入口 + 空状态说明；不默认创建。
- **报告负担**：thread 要写报告，可能被模型忽略。缓解：工具 guidance + 协调者上下文明确“没有报告就不算完成”。
- **状态膨胀**：报告/事件越积越多。缓解：协调者只读最近 12 份；完整文件留盘。
- **协调者失真**：只读状态仍可能编造。缓解：gate/证据契约；回答必须引用 report_id。

## 10. 已验证（2026-10-22，MVP 机制）

- 3 个真实 thread + worktree + `project_report`，Overview 实测 `review 2 / done 1`；
- 新协调者重建 prompt 39,097 字符，包含 thread 标题/摘要/gate；
- 同文件冲突返回 `site/README.md`，按 worktree 侧收口，主工作区干净；
- 合并后五道门禁全绿；
- 发现的缺口：报告可“假绿”（T3 声称 gates 全绿，但 e2e 在独立项目下实际失败）；证据存在性已暴露，gate 自动重验未做。
- 详细记录：`docs/COORDINATOR-P0.md`。

## 11. 验证计划

1. 用本仓库自身做一个 3-thread 项目（例如：官网、协调者文档、测试）；
2. 每个 thread 用 worktree，写 `project_report`；
3. 制造一次同文件冲突；
4. 新开协调者会话，问“谁在等我/哪些 gate 过了/下一步是什么”；
5. 记录：上下文长度、报告拒绝次数、冲突收口结果、协调者回答是否正确；
6. 根据结果把本 ADR 标为 Accepted 或回退 A。
