# 长程目标模式（Long-horizon Goal Mode）设计

- 状态：**设计（待实现）**
- 日期：2026-11-03
- 取代：`AUTONOMY-PLAN.md` 的“仅 run-scoped、不做目标”的结论；run-scoped 自主执行保留为其子集
- 目标：用户给意图与原则，系统深度分析后形成**稳定的里程碑计划**并自主推进；不逐步要用户点“继续”，不把长目标拆成会互相推翻的短目标

## 1. 先回答：DSH 的目标模式为什么让你反感

你反对的不是“有目标”，而是这套结构：

```
用户给一个长目标
  → 模型每轮临时定一个“下一步小目标”
  → 做一小步，重新观察，再定下一个小目标
  → 下一个小目标可能推翻上一个小目标
  → 拆分粒度不可控，经常只是“读文件/跑一次测试”这种无意义小步
```

根因不是“目标”两个字，而是：

| 根因 | 后果 |
|---|---|
| 目标是**每轮临时生成**的，不是持久契约 | 目标漂移、前后不一致 |
| 规划与执行在同一个循环里，**边做边规划** | 局部最优、短视 |
| 没有**全局计划/里程碑** | 不知道现在走到整体哪一步 |
| 没有**验收标准/证据** | “做完了”靠模型自述，短步空转 |
| 重规划**无约束** | 新想法一来就推翻旧步骤 |
| 完成定义是“本轮没有 tool call” | 一步就停，或无限微步 |
| 上下文压缩可能丢掉目标 | 做着做着忘了为什么做 |

所以正确方向不是“取消目标”，而是：**把目标变成稳定契约，把计划变成一次性深规划的里程碑，把执行变成按阶段验收，把重规划变成有证据、有边界的事件。**

## 2. 设计原则

1. **目标契约稳定**：意图、原则、非目标、验收标准在目标创建时确定；只有用户显式改意图，或证据证明契约不可满足，才允许改。
2. **先深规划，再执行**：规划阶段只读分析（可读代码/文档/跑只读检查），一次性产出覆盖整个目标的里程碑计划；执行阶段不再“每轮重新规划”。
3. **计划按“结果”拆，不按“动作”拆**：每个阶段是一个可独立验收的交付物/行为/决策，不是“读文件”“跑测试”这种动作。
4. **阶段内自由，阶段间稳定**：具体工具、命令、实现路径可随证据调整；阶段的 outcome/acceptance 不随意改。
5. **验收靠证据，不靠自述**：阶段门禁执行确定性检查（命令/测试/产物/差异），模型说“完成”不算。
6. **重规划是事件，不是习惯**：只有证据触发、版本化、保留已完成阶段；禁止“想到新点子就重写计划”。
7. **目标持久、执行可恢复**：目标/计划/证据落库，应用重启后继续；不是每轮临时目标。
8. **默认不设预算**：用户预算充足时不因 token/时间/轮数停；只按“目标完成/阻塞/无进展/审批”停。
9. **人只处理机器不该决定的事**：审批/不可逆、真正歧义、契约冲突、用户改目标；其余自动。
10. **可审计**：计划版本、决策记录、阶段证据、重规划原因全部可查。

## 3. 两种自主级别（自动选择）

| 级别 | 适用 | 行为 |
|---|---|---|
| **Run 自主** | 单阶段任务、问答、一次性修改 | 当前 `AUTONOMY-PLAN` 的 run-scoped 自主：同一 run 内自动继续，不建目标 |
| **Goal 自主（默认用于多阶段任务）** | 需要多个里程碑/交付物的长任务 | 目标契约 + 深规划 + 阶段执行 + 自动推进；跨 run/重启持久 |

自动判断：

- 规划器先做“任务分类”：单阶段（一个可验收交付）→ Run 自主；多阶段 → Goal 自主；
- 用户可显式说“按目标做/不要目标”，覆盖自动判断；
- 纯问答/解释不建目标，不自动继续。

## 4. 目标契约（Goal Contract）

创建后默认不可变：

```ts
interface GoalContract {
  id: string;
  sessionId: string;
  statement: string;          // 用户意图（原话 + 规范化重述）
  principles: string[];       // 用户给的原则/偏好/约束
  nonGoals: string[];         // 明确不做的事
  acceptance: Acceptance[];   // 整体完成的验收标准
  constraints: string[];      // 时间/技术/兼容/安全约束
  createdAt: number;
  version: number;
}
```

规则：

- 模型必须先把用户意图重述为 `statement` + `principles` + `nonGoals` + `acceptance`；歧义时才问用户（最多一次澄清）；
- 契约变更只能由用户显式改意图触发，或“证据证明不可满足”时提出，且需要记录 `contractChange`；
- `acceptance` 必须可验证；不可验证的（“做得好”）必须转成可检查的代理标准。

## 5. 深规划（一次性，只读）

### 5.1 规划阶段

- 规划器可读代码/文档、跑只读检查、列文件；**禁止写文件/改工作区**；
- 输出一份覆盖整个目标的**里程碑计划**，不是下一步动作；
- 规划完成后自动进入执行；计划展示在 UI，但**不要求用户点批准**（除非契约歧义/不可逆）。

### 5.2 计划模型

```ts
interface GoalPlan {
  goalId: string;
  version: number;            // 每次重规划 +1
  strategy: string;           // 总体策略（一段话）
  invariants: string[];       // 执行中必须始终成立
  phases: Phase[];            // 3–12 个里程碑（按结果拆）
  revisionLog: PlanRevision[];
}

interface Phase {
  id: string;
  title: string;
  outcome: string;            // 用户可见的交付物/行为/决策
  acceptance: Acceptance[];   // 本阶段完成的客观检查
  dependsOn: string[];        // 阶段依赖（DAG）
  risks: string[];
  status: "pending" | "active" | "done" | "blocked" | "rework";
  evidence: Evidence[];       // 命令输出/测试/文件/截图摘要
}
```

### 5.3 计划校验（防“短步目标”）

规划结果必须通过校验，否则重规划：

1. **结果导向**：每个 phase 的 `outcome` 必须是可交付结果/行为/决策，不能是“读 X”“跑 Y”“看一下”这类动作；
2. **可验收**：每个 phase 至少一个 acceptance（命令/测试/产物/行为检查）；
3. **覆盖整体**：goal acceptance 的每一条都能映射到至少一个 phase；
4. **依赖无环**：DAG 校验；
5. **粒度合理**：phase 数量 3–12；少于 3 说明可能该走 Run 自主；多于 12 要求按结果合并；
6. **不重复**：不允许两个 phase 做同一 outcome；
7. **不变式明确**：invariants 非空（至少包含用户原则/安全边界）。

校验失败 → 规划器重写（有次数上限），不允许把“动作”硬塞成 phase。

### 5.4 规划提示词要点

- 先分析：用户真正要的结果、约束、风险、可选路径、为什么选这条；
- 再给里程碑：每个阶段的 outcome/acceptance/deps/risks；
- 明确 invariants/non-goals；
- 明确“执行阶段不需要再问用户”的边界；
- 计划必须覆盖整个目标，不允许“先做第一步再看”。

## 6. 执行：Goal Runner

```
Goal created
  → Planner (read-only) → validated plan v1
  → Phase 1: execute until acceptance
       ├─ 同一阶段内可多轮工具/自我修复（Run 自主）
       ├─ 阶段门禁：跑 acceptance 检查
       ├─ 不通过：阶段内重试（最多 3 次）→ 仍失败则触发重规划/阻塞
       └─ 通过：写 evidence，标记 done
  → Phase 2 …（自动，无用户点击）
  → 全部 phase done + goal acceptance → 最终验收 → 完成
```

要点：

- **每个阶段是一次“大 run”**：内部可用现有 agent loop 多轮执行；阶段边界是持久检查点；
- 阶段内允许自主重试/换实现路径，但不改阶段 outcome/acceptance；
- 阶段门禁由 **Goal Runner 执行确定性检查**（不是模型自述）；检查失败把证据喂回模型继续修；
- 阶段完成后，下一阶段自动开始；用户只看到“阶段 2/5”；
- 每次阶段开始/结束写事件、证据、决策记录；
- 取消/停止立即中止当前阶段，目标保留为 paused。

### 6.1 阶段内自主（Run Autonomy）

- 模型在阶段内没有 tool call 但 acceptance 未达成 → 自动追加继续指令（同一阶段 run）；
- 阶段内预算默认不设；靠“无进展/重复失败”停；
- 阶段内最多 3 次连续无进展 → 阶段失败，进入重规划或阻塞。

## 7. 重规划（受控）

### 7.1 允许触发

| 触发 | 例子 |
|---|---|
| 证据推翻假设 | 测试证明方案不可行、依赖不存在 |
| acceptance 不可达 | 原验收在当前约束下无法满足 |
| 不变式/非目标冲突 | 新方案违反用户原则 |
| 阶段连续失败 | 3 次修复仍不通过 |
| 用户改目标/原则 | 用户显式修改 |

### 7.2 禁止触发

- “下一步不知道怎么做”（这是执行问题，阶段内解决）；
- “想到更好的点子”（除非证据支持且不推翻已完成）；
- “某个工具失败一次”（先重试/换路径）；
- “阶段太难”（先分解执行策略，不改计划）。

### 7.3 重规划约束

- 版本化：`plan vN → vN+1`，记录 trigger/evidence/diff/why；
- **已完成阶段不可删除/改写**；如发现缺陷，新增 `rework` 阶段并标记回归，不抹掉历史；
- 未完成阶段可调整顺序/合并/拆分，但必须保持 outcome 覆盖和依赖无环；
- 契约不变；若契约需变 → 必须用户确认；
- 重规划次数上限（默认 5）；超过则目标 `blocked`，给用户看证据。

## 8. 预算：默认不设

- `budget.mode = unlimited` 默认：**不因 token/时间/轮数停止**；
- UI 显示用量（token/时长/阶段数），只做提示，不做停止；
- 可选 `capped`：用户可设上限，达限暂停而非失败；
- 无预算时的停止条件只剩：
  - 目标完成；
  - 需要审批/不可逆；
  - 真正歧义/缺关键信息；
  - 无进展（阶段内 3 次无 evidence 变化）；
  - 连续失败；
  - 用户停止；
  - 上下文/存储不可恢复。
- 不把“成本”当默认停止理由；用户预算不足可自己设 cap。

## 9. 目标持久化与恢复

- 存储：`goals`、`goal_plans`、`goal_phases`、`goal_evidence`、`goal_decisions`（SQLite；JSONL 审计副本可选）；
- 一个会话最多一个 active goal；其他目标 paused/archived；
- 应用重启后，打开会话时自动恢复 active goal（默认 `resumeOnOpen=true`），从当前 phase 继续；已完成 phase 不重跑；
- 阶段中断：标记 `interrupted`，重进 phase 时先检查 evidence/工作区，避免重复副作用；
- 不恢复“正在执行的工具进程”；重启后重新评估当前状态；
- 目标完成/阻塞/暂停都持久化，历史可查。

## 10. 上下文与压缩

- 每轮 prompt 固定注入：
  - Goal contract 摘要（statement/principles/nonGoals/acceptance）
  - Plan 摘要（phases 状态、当前 phase、依赖）
  - 当前 phase 的 outcome/acceptance/invariants
  - 最近 evidence/决策（有界）
- 目标/计划**不依赖对话历史存活**；压缩后仍从存储注入；
- 已完成阶段只保留摘要 + evidence 引用，不重复全文；
- 压缩不能删除 goal context（单独注入，不参与普通历史压缩）。

## 11. UX（尽量无感）

- 创建目标后自动开始；**没有“继续”按钮**；
- 状态：`目标执行中 · 阶段 2/5 · 自动推进`；显示当前 outcome；
- 可展开“计划/证据/决策日志”；
- 只有四类打断：
  1. 审批/不可逆；
  2. 真正缺信息（澄清）；
  3. 目标 blocked（重规划超限/无法满足）；
  4. 用户主动停止/改目标；
- 审批通过后自动继续当前阶段，不需要再点；
- 完成：最终验收 + 用户可读总结（做了什么、证据、未做/风险）；
- 设置：`长程目标模式：自动/关闭`（默认自动）、`启动时恢复目标`（默认开）、预算（默认不限，可选上限）。

## 13. 判据（先写红，再实现）

- `GOAL-1` 多阶段任务自动建目标；单阶段/问答不建；
- `GOAL-2` 深规划只读（无写工具调用），计划通过校验；
- `GOAL-3` 计划拒绝“读文件/跑测试”这类动作型 phase；
- `GOAL-4` 阶段门禁以 acceptance 证据为准，模型自述“完成”不算；
- `GOAL-5` 阶段完成自动进入下一阶段，不需要用户点击；
- `GOAL-6` 阶段内无 tool call 且 acceptance 未达成 → 自动继续（同一阶段 run）；
- `GOAL-7` 阶段连续 3 次无进展 → 停止/重规划，不无限空转；
- `GOAL-8` 重规划只在允许触发时发生；版本化、保留已完成阶段；
- `GOAL-9` 契约变更必须用户确认；模型不能自行改 principles/nonGoals；
- `GOAL-10` 应用重启恢复 active goal，已完成阶段不重跑；
- `GOAL-11` `budget=unlimited` 不因 token/时间/轮数停止；`capped` 达限暂停；
- `GOAL-12` 压缩后 goal context 仍存在，阶段不丢；
- `GOAL-13` 审批暂停、批准后自动继续；拒绝则 blocked；
- `GOAL-14` 用户停止立即中止，目标 paused；
- `GOAL-15` 事件/日志完整：计划版本、阶段证据、重规划原因可查。

变异自证：删计划校验、把阶段门禁改成模型自述、允许无证据重规划、去掉 goal context 注入，均应变红。

## 15. 风险与对策

| 风险 | 对策 |
|---|---|
| 深规划本身错了 | 计划展示 + 用户可随时改契约；阶段门禁暴露偏差；重规划有证据 |
| 阶段过大/过小 | 校验 3–12 且结果导向；真实任务调参 |
| 无预算烧钱 | 默认不限但显示用量；用户可设 cap；无进展/失败停止 |
| 自动改计划 | 禁止无证据重规划；版本化；已完成不可删 |
| 重启恢复重复副作用 | 阶段 evidence/工作区检查；interrupted 标记；不重跑已完成 |
| 模型绕过验收 | 确定性检查；模型自述不算 |
| 目标漂移 | 契约不可变；变更需用户确认 |
| 与旧 goal mode 混淆 | 本文 ADR + 规则明确“长程里程碑目标”与“短步目标”区别 |

## 16. 与 DSH 的关键差异（一句话）

DSH：**目标在每轮临时生成，计划是短步队列，重规划无约束。**
本设计：**目标是一次契约，计划是一次深规划的里程碑 DAG，执行按阶段验收，重规划是带证据的版本事件。**

## 17. 需要你拍板的默认值

1. 目标模式默认：**自动**（多阶段任务自动建目标）还是仅显式开启？建议自动；
2. 预算默认：**不限**（你的要求）还是给一个很高的软上限？建议不限 + 显示用量；
3. 阶段数范围：3–12 是否合适？
4. 应用重启是否自动恢复目标？建议是（打开会话时），可在设置关闭；
5. 重规划上限：默认 5 次是否合适？
