# 分析：为什么"任务跑一轮就停"与"水位满了自动压缩"，Codem 有没有同类问题

> 2026-11 ｜ 对照 DSH（本会话的开发平台）与 Codem 1.16.334 的循环/压缩实现
> 结论先行：**第一种停（一轮就停）Codem 有同类问题**；**第二种停（压缩导致中断）Codem 的机制明显更好，
> 但在"单轮超长任务"上仍会主动放弃**。下面给证据、给方案。

---

## 1. DSH 的两种"停"是什么机制

### 1.1 分步任务做一轮就停

DSH（以及绝大多数 ReAct 式 harness）的"一次任务"边界是：

```
模型一次回复里还有 tool call ⇒ 继续下一轮
模型一次回复里没有 tool call ⇒ 这一轮结束，控制权交回用户
```

这是**协议级**的终止条件，不是"任务完成"判定。于是模型只要在某一步用自然语言说
"接下来我会…/现在开始…"而没有真正发工具调用，回合就结束了 —— 看起来像"干了一步就停"。
DSH 的 goal mode 用"外部续跑"绕过它（每轮结束再塞一条继续指令），但这属于平台层机制，
不是模型/循环本身保证的；不开 goal 时就没有续跑。

### 1.2 对话水位快满 → 自动压缩

DSH 在上下文接近窗口时压缩历史（摘要替换早期消息）。压缩本身有三种"停"的副作用：

1. **压缩发生在回合边界**：压缩后若控制权回到用户，任务线程就断了；
2. **摘要替换掉当前任务的关键状态**（目标、已改文件、待办、失败命令），模型下一轮"忘了自己在干什么"；
3. **工具调用与结果被截断/丢弃**：assistant(tool_calls) 与 tool 结果必须成对，压缩最容易在这里切错，
   模型看到"调过工具但没有结果"就重试或改口。

## 2. Codem 的现状（代码证据）

### 2.1 一样的问题：没有"任务级续跑"

`agentic-loop` 的循环同样以"没有 tool call"为出口；现有的 `completionNudges` 只在
**验证/回归**两类收尾守卫触发时补一轮（`agentic-loop.ts:644`、`:652`、`:1082`），
没有"待办没做完就继续"的通用策略。所以模型纯文本收尾时，Codem 和 DSH 一样会停。
（`maxIterations: 0` 表示不限制迭代数 —— 限制不在次数，而在"没有工具调用就退出"。）

### 2.2 压缩：Codem 已经比 DSH 细

- **循环内压缩**：每次迭代前按压力触发（`agentic-loop.ts:2681` 附近），不是等回合结束；
- **两级压缩**：50% 压力先做 `microCompact`（把旧工具结果裁成头尾，`micro-compact.ts:63` 保留最近 10 条）；
  70% 压力做结构化摘要压缩（`compaction-budget.ts`：`planCompactionKeep` / `alignKeepToRoundBoundary` /
  `selectMessagesByPriority` / `packPartsForSummary`）；
- **边界安全**：保留集必须落在 assistant/user 边界，且收缩用"向下对齐"（`alignKeepToRoundBoundaryDown`），
  避免从工具块中间切开；
- **结构化摘要**：`renderStructuredHistorySummary` + 压缩标记折叠，早期摘要不会越滚越大。

这些正是"优先压工具调用、保留最近几轮、按边界切"的正确做法，**Codem 大部分已经实现**。

### 2.3 仍然存在的 CodeM 问题（用户说的"同一轮超长任务"）

1. **单轮超长时提前认输**：`doCompactMessages` 里如果保留集本身超出预算，会置
   `overBudget` 并把 `consecutiveCompactions` 顶到 3（`agentic-loop.ts:6176` 附近），
   下一轮直接 `context_overflow` 结束并提示"请开启新对话"。
   而"保留集超预算"的常见来源正是最近 10 条里的大工具结果 —— `microCompact` 明确保留最近 10 条不折
   （`micro-compact.ts:66`），所以**最新的大输出永远不会被压**，只能整段放弃。
2. **连压熔断按"次数"而不是"效果"**：成功压缩后 `consecutiveCompactions++`，
   只有压力回落到阈值以下才清零（`agentic-loop.ts:2727` 附近）。
   一个持续高水位、但每次压缩都在**有效减重**的长任务，也可能在第 3 次被熔断
   （"即使压缩后仍无法继续"），这与"一直执行一直压缩"的目标相反。
3. **没有"段"概念**：压缩只按消息条数/轮次保留，不能把**当前这一轮**切成段、优先压最老的段，
   也没有段级 checkpoint 让压缩后从当前段继续。于是"一轮 200 次工具调用"只能整体保留或整体放弃。

## 3. 方案

### P1 · 任务级续跑（解决"一轮就停"）

**状态**：run 内维护 `taskLedger`（目标、待办清单、已完成、下一步、阻塞项）。待办直接复用 `show-todo`
写入的会话级 todo，不新造一套。

**回合结束判定**（在"模型无 tool call"之后、真正 `end` 之前）：

```
若存在未完成 todo / 明确的下一步，且本轮没有向用户提问、没有等审批、没有阻塞项，
且本轮确实做了工具调用（有进展证据）  ⇒ 自动续跑一轮（注入"继续执行未完成项，不要只描述"）
```

**护栏**：
- 续跑预算可配（默认 6 次），每次都显示"自动续跑 n/6"并可被停止按钮打断；
- **进展守卫**：连续两次续跑都没有新的工具调用、todo 状态也没变 ⇒ 停（不空转）；
- 用户提问/审批等待/失败重试耗尽 ⇒ 停；
- 与 DSH goal mode 的区别：这是**单次请求内**的续跑，不跨会话、不持久化目标，不改变"用户随时可打断"。

### P2 · 分段滚动压缩（解决"同一轮超长 + 水位"）

**段模型**：以 `assistant(tool_calls) + tool 结果` 为**原子**，把当前 user turn 切成若干段
（段 = 连续若干工具对 + 文本），段有稳定 id。当前正在执行的工具对是"活动段"，永不压。

**水线（软/硬）**：
- 60%：后台/迭代间隙折叠**已关闭段**里的工具结果（一行摘要 + 全文指针，复用现有溢出文件）；
- 80%：把最老的**已关闭段**整体摘要成"段摘要"（目标/改动文件/命令结果/错误/未决），插在保留集前；
- 90%：先折叠"最近 10 条"里的历史工具结果（保留活动段），再走整段摘要；
- 只有单条消息本身就超预算时才报"单条过大"（现在 `overBudget` 的诚实出口保留，但只作为最后一步）。

**压缩阶梯（优先压没用的）**：
1. 已关闭段里的工具输出 → 头尾 + 指针；
2. 已关闭段的整段 → 结构化段摘要；
3. 最近 10 条里的**历史**工具结果（非活动段）→ 头尾 + 指针；
4. 最后才动保留集条数（现有 `planCompactionKeep`）。

**同轮拆分执行**：每个段结束写一条 checkpoint（段 id、涉及文件、待办快照）到会话日志；
压缩后把"段摘要"作为新的前缀，循环**从当前段继续**，不重开 run、不丢工具配对。
这样"一直执行、一直把前序压掉"成立，且压缩后仍知道自己在第几段、还剩什么。

### P3 · 熔断按效果而非次数

- 每轮压缩前后各量一次压力；**压力下降 ≥ 5%（或移除条数 > 0 且压力下降）⇒ 清零计数**；
- 只有"压完仍不降"（含 `overBudget`）才累加，连续 3 次才 overflow；
- 这样长任务在持续减重时不会被误杀。

### P4 · 判据（先写判据再改）

| 判据 | 场景 | 必须证明 |
|---|---|---|
| CONT-1 | 脚本化模型：有未完成 todo 时纯文本收尾 | 自动续跑，且第 2 次后 todo 完成才停 |
| CONT-2 | 连续两次续跑无工具调用 | 停止，不空转 |
| CONT-3 | 用户提问/审批等待 | 不续跑 |
| SEG-1 | 单轮 200 个工具对，压力 85% | 循环内分段压缩，run 不中断，工具配对完整 |
| SEG-2 | 单条工具结果 200KB | 先折叠该结果（指针保留），不报 overBudget |
| SEG-3 | 90% 水位 + 活动工具调用 | 活动段不压，其余按阶梯压 |
| BRK-1 | 连续 5 次"有效但未低于阈值"的压缩 | 不熔断，任务继续 |
| BRK-2 | 连续 3 次"压完压力不降" | 诚实 overflow 结束 |

### 开关与顺序

1. 先做 **P3（熔断按效果）**：改动最小、收益直接、风险可控；
2. 再做 **P2 的阶梯 1/3**（折叠工具结果，含最近 10 条里的历史结果）：不加"段"也能解决大部分单轮超长；
3. 再做 **P2 的段模型 + 同轮拆分 checkpoint**；
4. 最后做 **P1 续跑**（产品行为变化最大，默认开启但可关，且必须带进展守卫）。

## 3.5 落地状态（2026-11）

- **P3 已落地**：`nextConsecutiveCompactions`（按效果计数）+ 循环接线；判据 BRK-1/2（5 条）。
- **P2 阶梯 3 已落地**：`microCompact(msgs, {keepRecent})`；水位 ≥0.8 保留 5 条、≥0.9 保留 2 条，
  让"最近 10 条里的历史工具结果"也能折；判据 MICRO-9/9b（3 条，含配对不变量）。
- **P1 不做**：仓库硬规则第 9 条**禁止目标模式/自动续跑**（用户 2026-10-15 明确要求）。
  合规替代：模型无工具调用收尾且存在未完成 todo 时，**只显示"继续"一键**（用户点击才发下一轮），
  不自动开新一轮；这不改变既有终止语义，也不引入持久目标。
- **P2 段模型：评估后判定"现有压缩已覆盖"，不再单独实现**。
  证据：`doCompactMessages` 在**每次迭代前**触发（不是等回合结束），保留集按"最近 N 轮"且对齐到
  assistant/user 边界（`alignKeepToRoundBoundary`），因此**单个 user turn 内部**也会被滚动压缩、
  且不会切进工具块。段 id + checkpoint 只会增加可观测量，不增加"继续执行"的能力；
  真要做也该作为诊断（记录"第几段被压"），而不是新压缩器。避免为同一能力维护两套实现。

## 4. 一句话回答

- **"一轮就停"**：Codem **有**同样问题（终止条件相同、没有任务级续跑）。
- **"水位满了压缩"**：Codem 的压缩机制**比 DSH 完整**（循环内、两级、结构化、边界安全），
  但**单轮超长时**会因"保留集超预算"提前认输，且熔断按次数不按效果。
- 建议按 P3 → P2 阶梯 → 段模型 → P1 的顺序落地，判据先行。
